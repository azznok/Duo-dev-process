# Process rules (always loaded, with CLAUDE.md)

> WRITTEN BY: the owner (from the Duo-dev-process template). BUDGET: 110 lines. The duo proposes through
> `docs/QUESTIONS.md`. The PROJECT's rules are in `CLAUDE.md` and `docs/PROJECT-RULES.md`: nothing here
> repeats or weakens them.

## 1. The proof

- What the user **SEES**: an image produced by the project's screenshot command into `proofs/<nnn>/...`,
  put NEXT TO its reference image (`tests/golden/`) or the reference cited by the task
  (`tools/image/sheet.ps1`).
- What the user **DOES** is proven at two levels. (1) **Logic**: a scenario that drives the product through
  its commands/API, with its assertions. (2) **Anything touching controls, UI or camera**: an INPUT script
  that injects raw keyboard/mouse/touch events into the client (real or off-screen window) and ends with a
  capture. Level 1 does not prove the key -> command translation. Never an internal function call, never a
  teleport nor a cheat command instead of the gesture to prove.
- **A green test or a measure alone is never a visual acceptance.** The image next to the reference decides,
  judged by the reviewer (never the coder) with the `art-judge` skill; it accepts alone. **Make it exist
  first**: it accepts what exists, works and reads; gaps to the reference go to `docs/STATE.md` § Polish,
  chosen by the owner after playing/using it. Rejection: a broken capture.
- **The feel when playing/using** (controls, flow, balance): the owner, at the end of the milestone.
- Three repetitions at most of the same green check: the fourth proves nothing.
- Read thumbnails (`python tools/image/vignette.py`, <= 1280 px), never a full-size PNG. A detail:
  `tools/image/loupe.ps1`.

## 2. One task, one branch

- Message: `<type>(<scope>): <summary in English> (TASK <nnn>)`. `git status --short` first; an unexpected
  file over 10 MB is an alarm.
- Never `push --force`, `reset --hard`, `clean -fdx`, `add -f`, history rewrite. A mistake is fixed by a new
  commit (`git revert` if needed).
- The harness creates `task/<nnn>-<entry>` from `main`; the coder commits and pushes there; the harness
  merges it into `main` ONLY after `VERDICT: ACCEPT`. A single remote `origin`.
- LFS BEFORE the first binary: a new heavy type is declared in `.gitattributes` before being committed (a
  binary enters history forever).
- One build tag per day at most (`m<n>-build<k>`), set by the owner.

## 3. Secrets

- Never read, displayed, copied or committed: `.mcp.json`, `config/project.env` if it holds any, API keys,
  account ids.
- Keys live in the User environment variables. In a versioned file, only their NAME (`${MESHY_API_KEY}`).
- No account created, no terms accepted, no software installed, no purchase beyond a written budget, without
  the owner's explicit OK for THAT action.

## 4. Sound

- Agents NEVER play sound. The proof of a sound is its log line (file loaded, duration, trigger). The owner
  listens.

## 5. Long jobs

- **Never end your turn while a job runs** (build, app launched, bench, benchmark): the end of the turn kills
  it. Wait inside the turn (blocking command with a timeout, or <= 10 min waits re-reading the log).
- An exe launched and left open declares its PID (`bin/benches/bench_pid.*`); the harness also stops every
  exe of the duo's build folder at the end of the task (`bin/harness/stop-all.ps1`).
- A bench prints ONE verdict line and puts the detail in `logs/benches/<name>.log`; header of 2 lines (what
  it proves, how to call it) -> `python bin/benches/benches.py`.

## 6. Production

- One milestone at a time, tasks in backlog order (`docs/PLAN.md`).
- A playable/usable build at the end of each milestone, and every ~3 days of work as soon as there is
  something to see. An imperfect build beats an absent one.
- Every task has a timebox and a fallback. Box expired: deliver the fallback, write it down.
- No binary asset (model, sound, texture) until `docs/parking/ASSET-PIPELINE.md` is validated by the owner:
  everything is generated by code or comes from a free pack listed in `docs/CREDITS.md`.
- A migration (rewrite, system change) lists what it abandons.

## 7. Memory and documents

- Project and harness facts live in `docs/` (versioned), not in automatic memory. `MEMORY.md` stays tiny: a
  pointer to this repo.
- Every process document carries its WRITER and its BUDGET in its header. Over budget: split it (the old
  text goes VERBATIM to an archive, the current file stays short).
- Knowledge is never deleted: it is archived. `docs/journal/` is never loaded.
- `STATE.md` and `QUESTIONS.md` keep only what is open: a closed thing leaves.
- One source per fact: roadmap = `docs/ROADMAP.md`, backlog = `docs/backlog/`, decisions = `docs/adr/`
  (index `docs/DECISIONS.md`), questions = `docs/QUESTIONS.md`. Point to it, never copy.

## 8. The process grows with the project

The kernel (this file, `CLAUDE.md`) and thin domain skills at the start. The agents grow them DURING the
development:

- **A procedure done for the 2nd time, or a trap paid once** (obscure build error, changed API, hour lost):
  the coder writes or completes the domain skill IN the task's commit. `SKILL.md` <= 150 lines, clear
  description (when to use, when not), points to scripts and docs instead of copying them.
- **A routinely read document over its budget**: split it (verbatim archive + short current file).
- **A new tool or domain**: new skill + new `DOMAINS` value + its MCP wiring (ask: it is `bin/harness/`).
- **Process review** at each milestone end or ~15 tasks: skill `build-release` § Process review.
- **Split procedures, never hide code**: the whole repo stays readable.
- **Limits**: skills, docs (except the protected ones), benches and tools are created and changed freely.
  `bin/harness/`, the security rules (§2 to §4), `docs/VISION.md`, `docs/PROJECT-RULES.md` and this kernel
  beyond its budget need an owner decision (`docs/QUESTIONS.md`).
- **A generic lesson** (true for any project): one line in `docs/UPSTREAM.md`.
