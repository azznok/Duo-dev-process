# Architecture decision records

> WRITTEN BY: the template (format); ADRs by the coder or the reviewer, owner decisions recorded by the supervisor. BUDGET: 40 lines.
One decision = one file. Why one file each: two duos never edit the same file, and a decision is read
without loading all the others.

## The rules

- File: `docs/adr/NNNN-<slug>.md` (slug: lowercase ASCII words joined by `-`).
- Number: `powershell -File bin/harness/next-adr.ps1` (shared counter between duos: never pick it by hand,
  two duos would take the same number).
- First line, exactly (parsed by `tools/doc/adr.py`):
  `## ADR-NNNN — <title> — *<status>* (TASK <nnn>)`
  Status, e.g.: `Decided by the owner on YYYY-MM-DD`, `Proposed by the reviewer`, `Accepted`,
  `Superseded by ADR-NNNN`.
- Sections, in this order: **Context** (what forces a choice), **Decision** (what is chosen; lettered
  points a), b)... when several), **Consequences** (what it costs, what it abandons, what must follow).
- **Never rewrite an ADR.** A changed decision = a NEW ADR that supersedes it; the old one only gets its
  status changed to `Superseded by ADR-NNNN` (and an amendment line may be appended, dated).
- `docs/DECISIONS.md` is GENERATED by `python tools/doc/adr.py index` (the harness, after each merge
  into main). Never edit it; the gate refuses a task that touches it.
- An owner decision (an answered question) always becomes an ADR; the question leaves `docs/QUESTIONS.md`.
- Any new architecture decision (a module, a dependency of weight, a format, a rule) is an ADR in the
  task that makes it.

Example: `0001-record-decisions.md`.
